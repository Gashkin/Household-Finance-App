# GBD-14 — persistent Windows instance and authorised AIB feeds

Canonical story: https://www.notion.so/418d3419fef081808864ca465d4eff7a

## Release status and boundaries

Preparation is synthetic. No real AIB consent, provider production activation, account coverage, Windows device protection or successful live retrieval is claimed by code or CI. The story remains open until controlled Windows/owner validation, human merge and main verification. The instance serves the compiled React app and authenticated backend together on `http://127.0.0.1:8080`, without Node, Maven, a checkout or Java installation on the operator's machine. The release includes a Windows runtime.

## Install, use, update and recover

1. Obtain the Windows ZIP for the reviewed exact commit from **Windows release verification**. Confirm the workflow, repository/commit and review evidence; hashes detect corruption, not a malicious replacement of both manifest and files. Extract to an ordinary local directory; do not put a private key or financial files there. Run `Install.ps1` in Windows PowerShell under your private Windows account. Organisation script policies may require locally unblocking a downloaded trusted release; do not disable machine-wide script policy.
2. Choose a workspace password of 16–256 characters and save it in your password manager. Installation stores password and the connection encryption key using Windows current-user DPAPI, with an owner-only directory and ACL. They are not portable to a different Windows profile or device.
3. Use the **Household Finance** desktop shortcut. Open the displayed loopback URL and unlock. Keep the foreground window open; Ctrl+C stops the instance. Banking and AI egress are disabled by default. Manual and CSV operation remain available.
4. Data lives in `%LOCALAPPDATA%\HouseholdFinance\data`, separate from versioned executables. The live H2 database is **not application-encrypted**; disk encryption and a private OS account are required before real financial use. The bank-reference file is independently AES-256-GCM encrypted; its random key is DPAPI protected in `config.xml` and decrypted only for the backend process. The signing PEM is owner-only on the encrypted device, outside source and browser storage. An administrator, malware or another process running as this Windows user can access running secrets; this is not an isolated hardware vault.
5. Use **Backup & recovery** to download a separate passphrase-encrypted `.hfb` archive. Keep it away from this device, with the passphrase in a password manager. Verify restore into an empty synthetic instance before first real use. A recovery backup contains reviewed records, plans and histories; it excludes provider credentials, session/account references, signing keys and local settings. After recovery on a new device, provision a new private config and reconnect at the bank. Never put real backups in GitHub, chat or CI.
6. For updates stop the instance, verify an encrypted backup, extract the new reviewed package and run its installer. Versioned application files are staged and verified before atomically changing `active.txt`; data/config are preserved. Keep the previous release for diagnosis, but do not blindly run an old binary against a migrated database. Restore the matching pre-update backup into an empty replacement data directory if rollback is needed. Every new commit invalidates the production readiness receipt. Reinstalling an existing version must match the incoming manifest and complete file-hash set; a coherent but different local manifest is rejected without activation.
7. Readiness expires after seven days, is bound to the exact release and must be rechecked after any device/ACL/key change. An expired receipt stops production launch until checked; it does not delete records. Disable production in the private config through `Disable-Production.ps1` to continue manual/CSV operation if the readiness check is unavailable. No background refresh is installed.

## Production provisioning — no authentication before readiness

Engineering never receives or displays provider private keys, bank credentials, OTPs, account references or transactions. The owner can register a separate **PRODUCTION, AIS-only** application without authenticating to a bank. Use the exact callback `http://127.0.0.1:8080/bank/callback`. Keep its private PKCS#8 RSA key outside the checkout with owner-only ACL. Do not reuse a sandbox application or register PIS. Legacy /api/bank-sandbox routes are rejected in production so a stale synthetic client cannot silently acquire production semantics. Metadata verification rejects wrong environment, inactive application, a missing callback or services beyond AIS.

Before asking the owner to link accounts, independently review the exact implementation and synthetic test evidence, then complete Desktop checks: encrypted volume fully protected, private account/data/config/key ACLs, ordinary launch, update preserving synthetic records, file-backed restart, backup/empty-workspace restore and negative access/consent checks. `Readiness.ps1` checks device encryption through Windows CIM (inspection rights may require elevation under the same Windows identity), ACLs and exact release; it asks the local operator to attest the completed review/recovery evidence. The same instance mutex covers its entire config/key transaction and rejects readiness while the app or another configuration operation is running. The attestation is a local deployment gate, not cryptographic proof of an independent review. It makes no provider or bank request. Do not type the readiness phrase until these checks actually pass. BitLocker recovery material belongs in the owner's private recovery process, never an engineering artifact.

Only then does the owner personally use **Activate by linking accounts** in Enable Banking. That activation authenticates with AIB and restricts the application to linked accounts; it is a real bank action and is **not preparation**. It does not authorise the application's API session. Start the local app, acknowledge the disclosed read-only access and choose **Connect my AIB accounts**. The owner performs the second bank-controlled consent and selects only their own intended accounts. No AI agent enters or observes bank credentials. The application captures and immediately removes callback parameters, binds one-use state to the authenticated workspace session and exchanges the code server-side. Cancelled, wrong-session, expired or replayed callbacks fail.

## Import, renewal, deletion and incidents

Select the authorised account and matching local cash/debt ledger, with dated opening evidence. Fetch at most 90 days/500 transactions, up to four explicit refresh attempts per 24-hour connection window. Failed attempts consume budget; restart, forget and reconnect do not reset it. No scheduled bank activity runs. Review every row, pending status, transfers and overlaps before approval. CLBD/ITBD/OPBD balances are dated evidence, never automatically spendable cash; credit limits/available balances are excluded. Reconcile booked balances explicitly, then reuse the reviewed cash in Plan ahead and decisions. Missing stable transaction IDs, unsupported currency/types, repeated pages, oversize or partial failures reject the import. Reconnect uses stable source identity and transaction references to avoid duplicates; reusing the wrong ledger is rejected.

Consent expiry/status is displayed and revalidated at the provider before every fetch. Disconnect revokes the API session and clears local connection references; failed revocation remains durably blocked and retryable across restart. Local forgetting is explicit and does not revoke wider bank/provider consent, erase approved records, or delete backups. Forgetting is blocked while session revocation is pending; retain its reference to retry. If a successful/uncertain exchange provides no usable session ID, the unresolved state is durably blocked, since no safe DELETE target exists. Revoke at the bank/provider and use the separate explicit external-revocation confirmation before clearing it; do not claim the application verified that external action. To revoke all consent use AIB's **Manage Shared Account Information** or [Enable Banking consent controls](https://enablebanking.com/data-sharing-consents/). To erase all local financial records stop the app and run `Remove-LocalData.ps1`; it requires explicit confirmation and fixed private paths. This is logical deletion, not physical secure erasure. Delete separately retained backups and exported reports deliberately.

For suspected compromise stop the app; revoke consent at AIB/provider, revoke/rotate the application signing key, secure the Windows account/device, and rebuild/recover from a known reviewed release and encrypted backup. Do not attach raw logs, data folders, dumps, screenshots, keys or transactions to issues. A protected initialization marker distinguishes a deliberately provisioned empty workspace from a subsequently lost connection file. Missing initialized state, corruption or wrong keys stop production startup without overwriting it; deletion of the whole private data directory is a separate deliberate reset. Windows reparse points, including junctions, are rejected by both launcher and Java store checks. A failed/corrupt/wrong-key connection store must be investigated without overwriting it; manual/CSV remains available after deliberately disabling production. Keep a compromised device offline until assessed.

## Trust boundaries and verification

AIB → HTTPS Enable Banking AIS → exact HTTPS backend allowlist → bounded in-memory response → owner review → local ledger/H2 → forecast/decision/export. Only bank/provider receives bank authentication. Keys and provider references stay server-side, AES-GCM/DPAPI and ACL protected. No telemetry or bank data goes to model vendors. Local HTTP is loopback only; sessions are HttpOnly/SameSite, mutating requests require CSRF header/origin checks, and all data routes are protected. Public routes contain only the app shell and static assets. Callback responses use no-referrer, no-store and a same-origin CSP. A hostile local administrator/process remains out of scope for software-only isolation.

Synthetic protocol tests cover production metadata, payment rejection, signed transport, callback binding, partial pagination, duplicates, encrypted restart, tamper/wrong-key failure, persistent revocation failure and refresh budget. Existing file-backed recovery tests cover financial plans/ledger backup compatibility. Browser tests run a test-classpath-only production simulator against the compiled single-origin app; no runtime transport override is packaged. Windows hosted CI packages a runtime and verifies ACL/DPAPI, startup, shell/callback and authentication with synthetic data. Hosted CI cannot attest the owner's actual Windows disk, provider registration, registry entry or live AIB accounts.
