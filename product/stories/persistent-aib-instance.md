The earlier local attestation cannot clear the amended security requirements. ## Install, use, update and recover

1. Obtain the Windows ZIP for the reviewed exact commit from **Windows release verification**. Confirm the workflow, repository/commit and review evidence; hashes detect corruption, not a malicious replacement of both manifest and files. Extract to an ordinary local directory; do not put a private key or financial files there. Run `Install.ps1` in Windows PowerShell under a dedicated standard Windows runtime account that has no development, coding-agent or runner workloads. Do not reuse the coding/runner Windows profile for production. Organisation script policies may require locally unblocking a downloaded trusted release; do not disable machine-wide script policy.
2. Choose a workspace password of 16–256 characters and save it in your password manager. Installation stores password and the connection encryption key using Windows current-user DPAPI, with an owner-only directory and ACL. They are not portable to a different Windows profile or device.
3. Use the **Household Finance** desktop shortcut. Open the displayed loopback URL and unlock. Keep the foreground window open; Ctrl+C stops the instance. Banking and AI egress are disabled by default. Manual and CSV operation remain available.
4. Data lives in `%LOCALAPPDATA%\HouseholdFinance\data`, separate from versioned executables. The live H2 database is **not application-encrypted**; disk encryption and a private OS account are required before real financial use. The bank-reference file is independently AES-256-GCM encrypted; its random key is DPAPI protected in `config.xml` and decrypted only for the backend process. The signing PEM is owner-only on the encrypted device, outside source and browser storage. An administrator, malware or another process running as this Windows user can access running secrets; this is not an isolated hardware vault.
5. Use **Backup & recovery** to download a separate passphrase-encrypted `.hfb` archive. Keep it away from this device, with the passphrase in a password manager. Verify restore into an empty synthetic instance before first real use. A recovery backup contains reviewed records, plans and histories; it excludes provider credentials, session/account references, signing keys and local settings. After recovery on a new device, provision a new private config and reconnect at the bank. Never put real backups in GitHub, chat or CI.
6. For updates stop the instance, verify an encrypted backup, extract the new reviewed package and run its installer. Versioned application files are staged and verified before atomically changing `active.txt`; data/config are preserved. Keep the previous release for diagnosis, but do not blindly run an old binary against a migrated database. Restore the matching pre-update backup into an empty replacement data directory if rollback is needed. Every new commit invalidates the production readiness receipt. Reinstalling an existing version must match the incoming manifest and complete file-hash set; a coherent but different local manifest is rejected without activation.
7. Readiness expires after seven days, is bound to the exact release and must be rechecked after any device/ACL/key change. An expired receipt stops production launch until checked; it does not delete records. Disable production in the private config through `Disable-Production.ps1` to continue manual/CSV operation if the readiness check is unavailable. No background refresh is installed.

## Production provisioning — no authentication before readiness

The owner can register a separate **PRODUCTION, AIS-only** application without authenticating to a bank. Use the exact callback `http://127.0.0.1:8080/bank/callback`. Keep its private PKCS#8 RSA key outside the checkout with owner-only ACL. Do not reuse a sandbox application or register PIS. Legacy /api/bank-sandbox routes are rejected in production so a stale synthetic client cannot silently acquire production semantics. Metadata verification rejects wrong environment, inactive application, a missing callback or services beyond AIS.

Before asking the owner to link accounts, independently review the exact implementation and synthetic test evidence, then complete Desktop checks: encrypted volume fully protected, private account/data/config/key ACLs, ordinary launch, update preserving synthetic records, file-backed restart, backup/empty-workspace restore and negative access/consent checks. `Readiness.ps1` first rejects the held release and privileged runtime identities. Once a subsequently reviewed release is cleared, it checks device encryption through Windows CIM, ACLs and exact release, then asks the local operator to attest the completed review/recovery evidence. Do not elevate the runtime identity to obtain inspection rights: arrange a separate administrator verification/read-only inspection capability, or retain the block. The same instance mutex covers its entire config/key transaction and rejects readiness while the app or another configuration operation is running. The attestation is a local deployment gate, not cryptographic proof of an independent review. It makes no provider or bank request. Do not type the readiness phrase until these checks actually pass. BitLocker recovery material belongs in the owner's private recovery process, never an engineering artifact.

Only then does the owner personally use **Activate by linking accounts** in Enable Banking. That activation authenticates with AIB and restricts the application to linked accounts; it is a real bank action and is **not preparation**. It does not authorise the application's API session. Start the local app, acknowledge the disclosed read-only access and choose **Connect my AIB accounts**. ## Import, renewal, deletion and incidents

Select the authorised account and matching local cash/debt ledger, with dated opening evidence. Fetch at most 90 days/500 transactions, up to four explicit refresh attempts per 24-hour connection window. Failed attempts consume budget; restart, forget and reconnect do not reset it. No scheduled bank activity runs. Review every row, pending status, transfers and overlaps before approval. CLBD/ITBD/OPBD balances are dated evidence, never automatically spendable cash; credit limits/available balances are excluded. Reconcile booked balances explicitly, then reuse the reviewed cash in Plan ahead and decisions. Missing stable transaction IDs, unsupported currency/types, repeated pages, oversize or partial failures reject the import. Reconnect uses stable source identity and transaction references to avoid duplicates; reusing the wrong ledger is rejected.

Consent expiry/status is displayed and revalidated at the provider before every fetch. Disconnect revokes the API session and clears local connection references; failed revocation remains durably blocked and retryable across restart. Local forgetting is explicit and does not revoke wider bank/provider consent, erase approved records, or delete backups. Forgetting is blocked while session revocation is pending; retain its reference to retry. If a successful/uncertain exchange provides no usable session ID, the unresolved state is durably blocked, since no safe DELETE target exists. Revoke at the bank/provider and use the separate explicit external-revocation confirmation before clearing it; do not claim the application verified that external action. Delete separately retained backups and exported reports deliberately.

For suspected compromise stop the app; revoke consent at AIB/provider, revoke/rotate the application signing key, secure the Windows account/device, and rebuild/recover from a known reviewed release and encrypted backup. Do not attach raw logs, data folders, dumps, screenshots, keys or transactions to issues. A protected initialization marker distinguishes a deliberately provisioned empty workspace from a subsequently lost connection file. ## Trust boundaries and verification

AIB → HTTPS Enable Banking AIS → exact HTTPS backend allowlist → bounded in-memory response → owner review → local ledger/H2 → forecast/decision/export. Only bank/provider receives bank authentication. Keys and provider references stay server-side, AES-GCM/DPAPI and ACL protected. No telemetry or bank data goes to model vendors. Local HTTP is loopback only; sessions are HttpOnly/SameSite, mutating requests require CSRF header/origin checks, and all data routes are protected. Public routes contain only the app shell and static assets. Callback responses use no-referrer, no-store and a same-origin CSP. A hostile local administrator/process remains out of scope for software-only isolation.

Synthetic protocol tests cover production metadata, payment rejection, signed transport, callback binding, partial pagination, duplicates, encrypted restart, tamper/wrong-key failure, persistent revocation failure and refresh budget. Existing file-backed recovery tests cover financial plans/ledger backup compatibility. Browser tests run a test-classpath-only production simulator against the compiled single-origin app; no runtime transport override is packaged. Windows hosted CI packages a runtime and verifies ACL/DPAPI, startup, shell/callback and authentication with synthetic data. Hosted CI cannot attest the owner's actual Windows disk, provider registration, registry entry or live AIB accounts.

## Amended security completion — evidence required to remove the hold

### Windows identity boundary

Use a new standard local runtime account, a separate browser profile and credentials never entered in a coding-agent or runner session. Keep all installation files, signing material, configuration, live data and local backups beneath its private instance root. Exported backups also require protected storage and a separate passphrase; browser Downloads, OneDrive/profile sharing and remote-control software can cross the boundary. Do not install development tools, agent extensions or a runner under this account. Do not give the development/runner accounts its password, runtime browser access, delegated administration, backup/debug privileges or access to its process token. A filtered administrator token is still an administrator identity and is rejected.

Run packaged `Test-IdentityBoundary.ps1 -Mode Runtime -RuntimeSid <local-runtime-SID> -InstanceRoot <private-root>` locally under the actual runtime user. It checks the entire private tree without reading contents and full encryption protection; reparse paths fail before descent. Prepare a private `backups` directory and synthetic installation first. Run `-Mode Excluded` with the same two parameters under **each actual development/agent and runner logon**, using Windows sign-in, never credentials in a script. It must show distinct standard users and five genuine access-denied checks for config/data and secrets/code/backups. Missing paths and other errors are inconclusive. Keep SIDs, user names and local paths in the operator's local record; only aggregate results belong in engineering evidence. These script outputs are audit aids, not signed authorisation or proof that all identities were inventoried.

An administrator or SYSTEM runner on the same host can cross ordinary account ACLs and read process memory. Do not claim isolation in that topology. Move the production instance to a separate trusted machine, or a VM whose host management is inaccessible to the untrusted development/runner identities, and verify shared drives, clipboard, remote sessions, credentials and management access. An administrator-controlled VM host is not an isolation boundary against that administrator. A future compromise of the deliberately trusted platform administrator remains a residual risk. The current Linux execution has not created or verified any Windows identity, effective denied access, encryption, startup/restart or restore on the owner's device. Those acceptance requirements remain blocked, not passed by the new helper.

### Provider enforcement and stolen signing credentials

Current [provider API reference, Payments](https://enablebanking.com/docs/api/reference/#payments) says production PIS requires separate provider enablement for licensed PISPs; sandbox enables it by default. Its application response exposes the services assigned to the signing key. This is documented provider-side separation, not merely our endpoint filter. Obtain a current production application configuration showing AIS only and provider confirmation that the specific key cannot invoke PIS or self-enable broader services. Do not send a payment request to test denial. Activation requiring account linking must wait until pre-authentication readiness is complete; if confirmation cannot be obtained beforehand, keep the hold.

Inference from the JWT authentication design: a stolen signing key permits requests directly to the provider outside this application's route, rate, state and local approval checks. If an attacker also obtains valid bank session/account references, assume authorised account-data disclosure and session deletion until provider/bank revocation or expiry; do not rely on AES-GCM after key/process compromise. Linked-account restrictions and bank SCA limit new consent but do not make a stolen key harmless. A documentation statement is not evidence of this registration's entitlement. No production key/configuration was available here, so actual AIS-only entitlement and direct-credential capability remain unverified. Reject PIS, mixed, unknown, empty or inactive metadata. Never reuse the sandbox key.

Public regulatory corroboration: [DNB register R183279](https://www.dnb.nl/en/public-register/information-detail/?registerCode=WFTBI&relationNumber=R183279), inspected 15 November 2026, identifies Enable Banking Oy under FIN-FSA supervision and lists account-information services for its Netherlands passport. This does not independently establish current Ireland passport scope. The EBA/Irish registration and owner-specific production eligibility still require confirmation. Existing free personal-use terms and AIB redirect documentation remain relevant; actual returned current/card coverage is not demonstrated, and AIB cards remain explicitly unverified.

The repository is currently **public**, independently observed through GitHub metadata. Treat historical financial information as potentially disclosed. Containment remains incomplete: the connected tooling has no repository-visibility mutation or authenticated provider-key revocation capability. Inspect historical private data locally and inventory forks, cached/hidden refs, releases, workflow artifacts, clones and copies. Rotate any genuinely exposed signing key, access token, application/workspace password or other reusable credential at its issuer, invalidate affected sessions and verify the old credential is revoked without publishing either value. No known live credential was identified or rotated here. No credential rotation or history purge is claimed. Retain this as a pre-live blocker until the owner-local assessment and required containment/rotation are evidenced. Any history rewrite is a separately reviewable owner-controlled operation, never an autonomous force-push.

Emergency sequence: stop the process and use `Disable-Production.ps1`; revoke bank/provider consent, then revoke the affected application key through provider controls. Bank revocation is owner-only. Generate a new production key within the isolated runtime profile and provision it locally after readiness; never overwrite a different existing key silently.
